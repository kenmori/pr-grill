# Reply モード(レビューコメントへの返信支援)

実際に付いたレビューコメントに、根拠付きの返信案(と必要なら修正案)を作る。
目的は「丸く収める」ことではなく、**レビュアーと作者の双方が正しい判断に早く到達する**こと。

## 1. コメントの取得
- 貼り付けられたらそれを使う
- `gh` が使えるなら未解決スレッドを自分で取る:
  `gh api repos/{owner}/{repo}/pulls/{n}/comments --paginate` と `gh pr view {n} --json reviews,comments`
- Step 1(コンテキスト収集)は必ず実施する。コメントの該当行だけでなく周辺を読む

## 2. コメントごとの分類
返信の前に、各コメントを次のどれかに分類し、作者に見せる:

| 分類 | 意味 | 基本方針 |
|---|---|---|
| バグ指摘 | 動作が間違っている/壊れるケースがある | 再現を確認して直す。直さないなら再現しない根拠を示す |
| 設計 | 置き場所・抽象化・方式への異論 | 却下案台帳と突き合わせる。作者の判断が要る → `[作者確認]` |
| 質問 | 意図・背景を聞いている | コードから答えられるなら `[コード根拠]` で即答案。意図なら `[作者確認]` |
| 好み・スタイル | 動作は変わらない | リポジトリの規約があればそれに従う。無ければ「従う」が既定(議論のコストの方が高い) |
| スコープ外 | この PR で扱うべきでない要求 | 別 Issue/PR を提案する返信案 |

## 3. 返信案の作り方
- 1 コメントにつき: 分類 / 返信案 / 必要なら修正の差分案 / ラベル(`[コード根拠]` `[推測]` `[作者確認]`)
- **レビュアーが間違っている可能性**があれば、遠慮せずそう言う。ただし返信案は「ファイル:行 では〜なので、この場合は〜になります。見落としがあれば教えてください」の形で、根拠を先に出し、断定を後にする
- 「対応します」とだけ返す案を作らない。何をどう変えるかを一文で書く
- 作者の意図が必要な返信は、作者に聞いてから確定する(Grill と同じく 1 問ずつ)
- 同じ論点が複数コメントにまたがる場合は、まとめて 1 つの返信にする案を出す

## 4. やらないこと
- 返信の投稿・スレッドの resolve は作者がやる。Claude は案を出すだけ
- レビュアーの指摘を小さく言い換えない。「ここは確かに〜」と認めるべきところは認める
- 修正を入れたら、Step 3 の想定問答を更新する(修正が新しい質問を生むことがある)
